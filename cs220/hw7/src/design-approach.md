okay let's take this approach. So for a Contract-First design, this requires me to identify what a component promises to provide before worrying about how it implements that behavior.

1. `SimulationObject` -> This is an object where it's main purpose is to build a foundation for all the types of objects that will be written on screen:
   1. `getLocation(): Coordinate` -> This is a method that, when called, will give the location of the current `SimulationObject` instance on screen. Note, though, that we won't be creating a `SimulationObject` instance directly but rather creating it through derived classes. I think that this implementation is going to be consistent throughout each derived class so we could probably write the implementation in this class directly instead of leaving it up to the derived classes if that's an approach we can take.
   2. `nextTick(): void` -> This is a method that, when called, will advance the next "tick" of the simulation on that object. It isn't expected to return anything but I feel that we should define what that behavior looks like for each derived class because the way a `SimpleLobster` might behave on `nextTick()` could be different from some other derived class.
2. `Agent` -> This is a derived class from `SimulationObject` that will "move towards a destination and exist in different states".
   1. `startMoving(destination: Coordinate, speed: number)`; -> This is a method that, when called, will move the `Agent` instance towards a destination (`Coordinate`) at some given velocity/speed (`number`). Again, because the behavior of this seems to be universal, I think the implementation can be done within this class directly without the need to leave it to other derived classes to override.
   2. One note, the spec says "You may add a constructor to the `Agent` class and override any base class methods you need to override. Any other methods or attributes you add to `Agent` must be non-public." however, I don't think that I would need to override `nextTick()` just yet considering that an `Agent` is too generic of an object in the context of this project where it would make more sense to implement that behavior directly in another layer of derived classes such as `SimpleLobster`
3. `SimpleLobster` -> This is a derived class from `Agent` that is rendered as with image ID `lobsterRegular` at a scale of `0.4`. The condition with an instance of a `SimpleLobster` is that once it reaches it's destination via `startMoving()`, it stops moving.
   1. `override nextTick()` -> I suggest an override to `nextTick()` here because the movement using `startMoving()` shouldn't be chaining but we need to track the state of that object that once `startMoving()` has been called and completed, we should set the behavior of `nextTick()` to set the behavior to essentially do nothing so it doesn't respond to further calls to the method.
4. `SleepyLobster` -> This is derived class from `Agent` that is initially rendered and behaves identical to a `SimpleLobster`. The major caveat is that once an instance of a `SleepyLobster` reaches it's destination (`Coordinate`) it was directed to move towards, it falls asleep. What this means is that we need to re-render the object with a new sprite using the image ID `lobsterSleeping` at a scale of `0.25`. Once in this sleeping state, this object should ignore all future instructions to move to a new destination.
   1. `override nextTick()` -> I suggest an override to `nextTick()` here because the movement using `startMoving()` shouldn't be chaining but we need to track the state of that object that once `startMoving()` has been called and completed, we should set the behavior of `nextTick()` to request a re-render change givin the proper image ID and scale and then set the behavior to essentially do nothing.
5. `agentFactory(type: str, initial_location: Coordinate)` -> This is a function that will create an instance of `SimpleLobster` when passed `"simple_lobster"` and create a `SleepyLobster` when passed the string `"sleepy_lobster"`. If passed anything other than these strings, it should `throw new Error("unsupported agent type: " + type)`.
6. `Structure` -> This is a derived class from `SimulationObject` that lives in `structure.ts`. It's purpose is to be the foundation for structure which are simulation objects that don't move after created at a location (`Coordinate`). If I decide to make any other methods in `Structure`, they need to be private.
7. `House` -> This is is a derived class from `Structure` that lives in `structure.ts`. It exists at a location (`Coordinate`) but has no functionality besides existing. It should be rendered with an image ID of `simpleHouse` at a scale of `1.0` (aka the default scale).
8. `structureFactor(type: string, location: Coordinate)` -> This is a function, when called, will create an instance of a House when passed the string `"house"`. If it is passed anything else, it should `throw new Error("unsupported structure type: " + type)`. The created house will stay at the location passed.
9. Controller (`main.ts`) -> This is where things will be created and where the simulation loop will run, which calls `nextTick()` on the model and re-draws the main view.
